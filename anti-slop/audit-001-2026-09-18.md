## Temuan

### 1. [HIGH] Verifikasi runtime belum dapat dilakukan

Bukti: PHP, Composer, vendor, node_modules, dan Docker Compose belum tersedia atau belum siap.

Dampak: perubahan performa, schema, copy, dan code tidak boleh dinyatakan aman hanya dari static inspection.

Rencana: siapkan verification lane terisolasi, jalankan migration fresh dan upgrade, composer test, PHPStan, Pint, TypeScript, lint, build, API test, dan smoke test web.

Rule: R-35, evidence over claims.

### 2. [HIGH] README bertentangan dengan runtime configuration

Bukti: README masih menjelaskan SQLite untuk session, queue, cache, dan Docker SQLite. compose.yaml menggunakan PostgreSQL dan Redis. .env.example juga default PostgreSQL.

Dampak: developer baru dapat menjalankan setup yang salah dan menghasilkan drift lokal dengan deployment.

Rencana: tulis ulang README berdasarkan jalur setup yang benar, pisahkan local Docker, local fallback, test, production, troubleshooting, dan batas verifikasi.

Rule: R-31, R-36.

### 3. [HIGH] Status ticket dan acceptance checklist tidak konsisten

Bukti: beberapa ticket berstatus Done, tetapi acceptance criteria masih unchecked. TASK-017 juga menyebut acceptance criteria belum dicentang dan deployment Coolify belum diverifikasi.

Dampak: status project tidak dapat menjadi sumber kebenaran lifecycle.

Rencana: pisahkan implementation status, verification status, environment blocker, evidence commit, dan deployment status. Jangan mengubah status menjadi verified tanpa evidence baru.

### 4. [HIGH] Nilai uang API berpotensi berbeda dari web

Bukti: InventoryApiController dan InventoryDashboardApiController melakukan cast harga ke integer. Database menyimpan harga decimal(15,2). Web memakai float.

Dampak: nilai pecahan dapat terpotong dan total API dapat berbeda dari total web.

Rencana: tetapkan money contract, gunakan decimal-preserving calculation, response serialization yang konsisten, lalu tambah test harga pecahan dan parity web/API.

### 5. [HIGH] Rate limiting API belum terbukti aktif

Bukti: Fortify web memiliki throttle login, tetapi route API tidak menunjukkan throttle yang eksplisit. Ticket dan keputusan project menyatakan rate limiting wajib.

Dampak: endpoint login dan resource API dapat menerima request tanpa batas yang terdefinisi.

Rencana: tetapkan limit per route group, dokumentasikan response 429, dan uji burst request pada API login serta resource.

### 6. [HIGH] Docker memakai credential default dan mengekspos PostgreSQL serta Redis

Bukti: compose.yaml menetapkan password database default dan mem-publish port 5432 serta 6379 ke host. entrypoint juga memiliki fallback password default.

Dampak: konfigurasi development mudah terbawa ke deployment dan service data dapat terekspos ke jaringan host.

Rencana: pisahkan compose development dan production, wajibkan secret dari environment, hilangkan port publish production, dan tambahkan startup fail-closed jika secret wajib kosong atau default.

### 7. [HIGH] Race condition register belum sepenuhnya diselesaikan

Bukti: service membaca register maksimum lalu insert. Unique constraint mencegah duplicate final state, tetapi concurrent request dapat membaca register yang sama dan salah satu transaksi gagal.

Dampak: request valid dapat gagal sporadis pada penggunaan multi-user.

Rencana: locking strategy pada parent item atau counter atomik, error contract yang jelas, concurrency test, dan retry hanya jika aman serta terbukti tidak menimbulkan efek ganda.

### 8. [HIGH] Statistik dashboard mencampur unit dan kelompok

Bukti: KPI kondisi dihitung dari inventory_units, sedangkan statistik tahun dan asal menggunakan count inventory_items.

Dampak: label aset dapat terbaca sebagai jumlah unit, tetapi nilai yang dikirim adalah jumlah kelompok barang.

Rencana: putuskan contract produk secara eksplisit, lalu gunakan label kelompok atau hitung berdasarkan unit dengan query aggregate yang konsisten.

### 9. [MEDIUM] Query dashboard berpotensi N+1 dan memuat data berlebih

Bukti: dashboard mengambil semua InventoryItem lalu memanggil units()->count() per item. Beberapa detail juga melakukan count setelah relation dimuat.

Dampak: waktu dan query bertambah seiring jumlah kelompok inventaris.

Rencana: pindahkan aggregate ke database, gunakan withCount atau join aggregate, pilih kolom yang diperlukan, dan ukur query count serta latency sebelum dan sesudah.

### 10. [MEDIUM] API pagination tidak memiliki batas maksimum yang terlihat

Bukti: endpoint menerima per_page dari request dengan default, tetapi tidak terlihat batas max.

Dampak: client dapat meminta page sangat besar dan meningkatkan penggunaan memory serta waktu query.

Rencana: validasi min/max, tetapkan default dan maksimum dalam config atau contract API, lalu tambah test batas.

### 11. [MEDIUM] Permission update keterangan memakai permission kondisi unit

Bukti: PATCH item web dan API menggunakan inventory.unit.condition.update, walaupun operasi hanya mengubah keterangan item.

Dampak: authorization tidak menggambarkan aksi sebenarnya dan sulit dikembangkan saat permission diperinci.

Rencana: tambah permission yang tepat untuk update item atau keterangan, migrasikan seeder dengan idempotent rule, dan uji matrix permission.

### 12. [MEDIUM] Guard role dan permission API perlu verification khusus

Bukti: seeder membuat role dan permission dengan guard web. API memakai Sanctum dan middleware can.

Dampak: akses dapat terlihat benar pada sebagian jalur tetapi gagal atau salah pada guard tertentu.

Rencana: uji token API untuk Super Admin, Admin Inventaris, Guru, user tanpa role, unauthorized, dan forbidden. Jangan membuat guard baru tanpa bukti kebutuhan package.

### 13. [MEDIUM] Detail API tidak tampak memiliki contract qty yang seragam

Bukti: list memakai units_count, detail memuat units dan total, sedangkan web menambahkan qty secara eksplisit.

Dampak: client API perlu menebak field yang harus dipakai.

Rencana: tetapkan API resource/DTO untuk InventoryItem dan InventoryUnit, dengan field qty, total, harga, dan money representation yang konsisten.

### 14. [MEDIUM] Konvensi prefix tabel belum memiliki taxonomy yang diputuskan

Bukti: tabel Laravel default, tabel Sanctum, Spatie, passkeys, inventory, cache, queue, dan session masih bercampur tanpa namespace nama.

Dampak: rename langsung berisiko memutus package, migration lama, foreign key, test, dan data existing.

Rencana usulan taxonomy bertahap:

- auth_users
- auth_password_reset_tokens
- auth_sessions
- auth_passkeys
- auth_personal_access_tokens
- m_roles
- m_permissions
- m_inventory_items
- tr_inventory_units
- sys_cache
- sys_cache_locks
- sys_jobs
- sys_job_batches
- sys_failed_jobs
- pivot_model_has_roles
- pivot_model_has_permissions
- pivot_role_has_permissions

Catatan: nama m_ dan tr_ perlu disepakati berdasarkan arti domain. Inventory units dapat dianggap master fisik atau transaksi aset. Jangan rename sebelum package table names, model table, morph relation, migration order, foreign key, and rollback path diuji.

### 15. [MEDIUM] Skema inventory belum memiliki taxonomy field dan constraint yang cukup eksplisit

Bukti: condition berupa string bebas dengan validasi aplikasi. Tidak ada enum atau check constraint yang terlihat. Harga decimal ada, tetapi API memperlakukannya sebagai integer.

Dampak: jalur database langsung atau bug pada aplikasi dapat memasukkan condition invalid. Contract money tidak seragam.

Rencana: tetapkan PostgreSQL check constraint atau enum yang kompatibel dengan fallback test, constraint domain yang aman, serta strategi decimal yang sama di seluruh jalur.

### 16. [MEDIUM] Search dan filter belum memiliki strategi performa yang lengkap

Bukti: search menggunakan LIKE pada beberapa kolom dan relation register. Index dasar ada, tetapi belum ada bukti query plan atau index untuk pola pencarian aktual.

Dampak: pencarian dapat melambat pada dataset besar.

Rencana: ukur EXPLAIN pada PostgreSQL dengan fixture realistis, evaluasi trigram atau prefix strategy bila diperlukan, dan hindari index sebelum query workload terbukti.

### 17. [MEDIUM] Code comments terlalu padat pada beberapa area

Bukti: static scan menemukan sekitar 292 comment markers pada application, route, database, dan frontend code. Beberapa komentar hanya mengulang code, memberi label generic, atau menjadi separator.

Dampak: noise meningkatkan beban baca dan menyamarkan komentar yang benar-benar penting.

Rencana: audit comment-only dalam batch terpisah. Hapus komentar yang obvious, pertahankan business rule, security, performance, concurrency, contract, workaround, dan licensing. Jangan mengubah executable code dalam batch ini.

Rule: antislop-code, R-31.

### 18. [MEDIUM] Copywriting masih bercampur bahasa produk dan template foundation

Bukti: sidebar dan search memakai Users, Search, Roles & Permissions. README memakai bahasa starter template. Landing page masih membawa copy dan visual Laravel starter.

Dampak: identitas sistem sekolah belum konsisten dan pengguna melihat istilah yang tidak seluruhnya sesuai bahasa produk.

Rencana: audit semua user-facing string, tetapkan glosarium Bahasa Indonesia, pisahkan label teknis yang memang harus tetap, lalu tulis ulang README dengan copy spesifik dan tanpa klaim yang tidak terbukti.

Rule: antislop-copywriting, R-02, R-15, R-16, R-36.

### 19. [MEDIUM] Ada karakter em dash pada UI dan dokumentasi yang menjadi target copy audit

Bukti: ditemukan pada title halaman inventaris, label kondisi, komentar, dan .env.production.example.

Dampak: bertentangan dengan mode audit antislop yang dipilih, kecuali konteks dokumentasi rule.

Rencana: ganti pada user-facing copy dan dokumentasi project yang akan dipublikasikan. Jangan ubah third-party generated content tanpa scope yang jelas.

Rule: R-02.

### 20. [LOW] External links dan copy foundation masih tersisa

Bukti: beberapa komponen navigasi masih memuat link Laravel starter kit, Laravel docs, X account, dan copy template.

Dampak: user dapat keluar ke tujuan yang tidak relevan dengan produk sekolah.

Rencana: inventaris link, tandai link yang memang dibutuhkan, hapus link template, dan jangan mengganti dengan link fiktif.

Rule: R-24, R-26, R-38.

### 21. [LOW] README belum menjadi dokumen operasional

Bukti: README hanya mencakup instalasi singkat dan scripts. Belum mencakup arsitektur nyata, environment matrix, database naming policy, API overview, troubleshooting dependency, deployment boundary, backup, rollback, dan verification evidence.

Dampak: onboarding dan operasi bergantung pada pengetahuan yang tidak tertulis.

Rencana: tulis ulang README setelah keputusan schema dan verification lane disepakati. README tidak boleh menyatakan build, test, deploy, atau security claim yang belum dibuktikan.

### 22. [LOW] Comment hygiene harus dilakukan per scope, bukan global blind deletion

Bukti: banyak comment pada komponen UI berasal dari foundation atau menjelaskan keyboard, SSR, accessibility, layout, dan workaround.

Dampak: pembersihan massal dapat menghapus informasi penting dan membuat regression lebih sulit ditelusuri.

Rencana: pertahankan komentar yang menjelaskan alasan, boundary, protocol, atau workaround. Hapus hanya komentar yang lolos klasifikasi sebagai redundant atau decorative.

Rule: antislop-code.

## Urutan pengerjaan yang disarankan

1. Verification lane dan baseline evidence.
2. Schema taxonomy decision serta compatibility mapping.
3. Data correctness: money, dashboard semantics, API contract.
4. Performance query audit berbasis EXPLAIN dan fixture.
5. Security and deployment hardening.
6. Code comment hygiene.
7. Copy audit dan README rewrite.
8. Final regression verification.

## Stop conditions

- Jangan rename tabel sebelum migration upgrade dan rollback diuji pada salinan data.
- Jangan menyatakan performance improvement sebelum ada before/after measurement.
- Jangan menyatakan build atau test lulus tanpa output baru dari environment yang sesuai.
- Jangan menghapus comment secara massal.
- Jangan mengedit temuan yang belum dipilih Tuan.
